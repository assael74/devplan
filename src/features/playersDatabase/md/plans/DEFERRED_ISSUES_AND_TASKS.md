# Deferred Issues and Tasks

**עדכון אחרון: 27.09.2026**

רשימת משימות פתוחות וממוקדות עבור Players Database. כל משימה מתעדת בעיה
שנדרשת לבחינה; היא אינה קובעת פתרון מראש.

## 1. בחינת מסמך Clubs Master

מסמך `dbClubsMaster/all` מרכז כיום 275 מועדונים, 512 קבוצות גיל ו־759 רשומות
עונה. הוא מכיל מידע מצטבר רב, בעיקר תחת `ageGroups` ו־`competitionPaths`, וכל
קריאה או כתיבה שלו מעבירה את המסמך השלם. יש לבחון האם גודל המסמך, שכפול נתוני
העונות והיקף העדכון המלא עדיין תואמים את תפקידו כ־projection מרכזי.


## 2. אחידות מזהי עונה במזהי Firestore

ערך עונה עסקי, כגון `26/27`, מופיע בחלק מהזרימות גם כחלק ממזהה מסמך או מזהה
SearchIndex. התו `/` אינו תקין בתוך מזהה שמועבר ל־Firestore כנתיב מסמך, ובנייה
ידנית ולא אחידה עלולה ליצור reference לא חוקי או לגרום לכך שה־writer וה־Audit
יפנו לשני מסמכים שונים. יש למפות את כל המזהים המשתמשים בעונה, להגדיר ייצוג
אחיד ובטוח ל־Firestore עבור מזהים בלבד, ולוודא שכל המסלולים משתמשים בו.


## 3. תיעוד שגיאות טעינה לצורך זיהוי כשלי שורש

יש לבנות תהליך ממוקד שמתעד כשלים בזרימות הטעינה באופן שמאפשר לזהות תקלות
חוזרות ואת סיבת השורש שלהן. יש לבחון אילו פרטים נדרשים לצורך אבחון, כגון סוג
הטעינה, מזהה ה־Receipt, השלב שנכשל, זהויות היעד, קוד השגיאה, הודעת השגיאה,
זמן הכשל ותוצאת ה־Audit האחרונה, בלי לשמור payload עסקי מלא או מידע שאינו
נדרש לאבחון. מטרת התהליך היא Observability ו־Root Cause Analysis; אין להפוך
אותו למנגנון Jobs, Retry או Recovery חדש.


## 4. Audit V2 ותיקון מפורש עבור טעינת קבוצות ליגה וטעינת סגל

יש לבנות עבור טעינת קבוצות / טבלת ליגה ועבור טעינת סגל תהליך מקביל לעיקרון
שהוכח במסלול Stats V2: Expected State ממקורות קנוניים, קריאת Actual State
ישירות מהשרת, השוואה לפי תחומי בעלות, Findings ו־Coverage מפורשים, הפעלה מחדש
של שלבי הסנכרון הרלוונטיים מתוך אותו Modal, Recheck וסגירת Receipt רק לאחר
בדיקה נקייה. יש לבנות כל Flow לפי החוזים והצרכים שלו, ולא ליצור מראש Framework
כללי משותף ל־League, Roster ו־Stats.
